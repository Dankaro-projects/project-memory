# Intent, continuation and Kanban verification

The next iteration connects a project's intended results to explicit work, bounded continuation and a live sprint board. It responds to the request for more autonomy without treating stored text as authority or hiding failed work. The [aggregate evidence](verification-autonomy-2026-09-14.json) contains measured results; raw host logs and operational databases remain private.

## What changed

An existing episode becomes a work card. Its objective and completion criterion retain the original intent. Append-only plans add scope, next action, ownership, readiness, sprint assignment and explained dependencies. Atomic `plan` and `sprint` operations avoid a separate task database and preserve optimistic version checks. An older database retains its rows and other validation checks when its first plan extends the existing event-type trigger.

`memory_get next` returns the named work, full scope and a checked continuation route. It identifies missing plans, proposals, stale evidence, blocked dependencies, another session's ownership, unconfirmed execution and completed work awaiting a state update. Recorded execution without an assessed outcome directs the agent to inspect existing results before repeating an outdated next action. A queued task does not authorise a switch of objective. Host hooks provide a pointer to active planned work; they do not launch another agent or schedule background work.

The live and offline HTML viewers add a read-only Kanban board. Users select a sprint and open cards to inspect intent, conditions, dependencies and complete paginated decision history. A successful outcome can release dependent work. Changed evidence can return a Done card to Review without rewriting its earlier state. Decisions retain the plan used at the time; changing scope or prerequisites flags their basis for review. Ordinary progress changes do not invalidate a decision. Writing, code and research remain separate subjects.

## Observed failures and their causes

The first prototype reached the correct result but made seven rejected memory requests. It requested unsupported budgets, confused a record kind with the atomic plan operation, omitted a host session, guessed later versions after failed writes and supplied incorrect revision fields. Tool guidance now names the continuation entry point and budget range. The response supplies the exact version and update operation, and the `work_plan` schema lookup directs the agent to `plan`. Validation remains strict; invalid writes are not silently repaired.

The next run repaired the parser and passed its tests but exceeded the harness's 240-second deadline before recording its outcome. That interruption remains a failed uninterrupted completion. Inspection found existing execution alongside an outdated saved next action. The continuation response now directs recovery to that evidence. Resuming the same actual Codex task in a fresh app-server process finished the records without a shell command or repeated repair.

Review also found an earlier decision's outcome appearing on its replacement decision. The card now selects an outcome by its current decision ID. A regression exercises a failed attempt followed by a revised choice and execution; the revised choice does not inherit the old assessment. Browser checks found hidden filters remaining visible and a writing-correction label reused for work scope. Both were corrected in the existing viewer. Upgrade inspection also found that a running older viewer could be reused after installing new code. The launcher now checks its package version and opens the current release at a new address while leaving the older process intact.

## Measurements

The release baseline is `f767918` (0.5.0b3): 130 tests passed and no work-plan or sprint board existed. The final suite passes 149 tests in 7.761 seconds on local Python 3.13.13. The tests cover actual SQLite state, version conflicts, preservation of old data, dependencies, stale evidence, current-decision outcomes, host receipts, context boundaries and a separate live HTTP process. Node checks execute the actual viewer script. Installed-wheel and MCP bundle checks execute the packaged server and viewer outside the checkout.

The invented repair requires strict UTF-8, rejection of invalid bytes, Latin-1 only on a tagged legacy endpoint and an explicitly unmeasured production effect. All completed model runs preserve those four facts, pass the three independent parser tests and return the requested JSON. The scripted baseline retains two failing tests before the successful repair; both assessments remain in its history.

| Actual Codex run | Result | Memory calls | Rejected requests | Largest reported full input |
|---|---|---:|---:|---:|
| First prototype | Completes; board shows Done | 30 | 7 | 29,687 tokens |
| Revised flow, before interruption | Tests pass; outcome remains missing at 240 seconds | 14 | 0 | 23,819 tokens |
| Same task resumed in a fresh process | Completes missing records; zero shell commands | 5 | 0 | 27,884 tokens |
| Final uninterrupted comparison | Completes; board shows Done | 15 | 0 | 24,657 tokens |

The first and final tasks use the same prompt, parser contract and completion checks. The dependent release claim is correctly classified as writing in the final fixture; it was code in the earlier fixture. The prototype was not committed separately, so its private logs establish the recorded result but not an independently replayable interim release. These are small engineering trials, not a controlled productivity study. The final current-decision outcome fix was subsequently checked by the regression suite. No rejected request or interrupted run is excluded from the report.

Actual hooks capture session start, the user prompt, decision binding, tool starts/results and stop. The final run records six tool-start/result pairs with no remaining execution issue. The recovery reuses real prior execution. This iteration does not independently prove that Stop context caused the agent's behaviour, or establish live Claude interruption behaviour; the earlier [feedback report](feedback-2026-09-14.md) documents the separate host checks.

The board scans matching work to check state and totals; its measured cost grows with the inventory. The named reply retains full intent and scope. Board and sprint pages reduce their card count to fit the reply budget and return `next_offset`; they never shorten a card’s scope. A regression reconstructs all 20 cards through the default budget without omissions. Character counts are not token estimates. Provider input counts include instructions, tool definitions, history, task and retrieved memory. Even with unrelated connectors and global memory disabled, the below-10K full-input target remains unmet. No condition or feature was removed to meet it.

Chrome inspection verifies 25 then four cards from 29 work items, sprint filtering, direct evidence links and live external updates. A completed repair becomes Done and releases dependent work. All 20 expanded history entries remain visible after another process appends a note. Changing the source file moves the open Done card into Review with a concrete reason; restoring it returns the current state to Done. The final labels identify work scope and plan evidence explicitly. An actual installed beta 3 viewer and the beta 4 launcher were exercised outside the source checkout: both used the same database, the new viewer exposed all three existing work cards, and the older viewer remained available. The first attempt ran inside the checkout and loaded the local package into the child process; its version assertion failed. Repeating the test outside the checkout established the intended installed-release boundary.

## Reproduce

From the source checkout, run:

```sh
uv run python -m unittest discover -s tests -q
node tests/viewer_logic.cjs
uv run python -m examples.planning_measure
uv run python -m examples.planning_case --project results/planning-demo --extra 26
uv run python -m examples.planning_demo --project results/planning-demo
uv run project-memory view --project results/planning-demo
```

Use fresh output directories. The demo executes the failing baseline and the repair; it rejects an already-used work history instead of repeating the action. The exported `completed-board.html` also works offline. Existing CI runs Chromium checks for board pagination, search, sprint selection, card scope, desktop and mobile layouts, while retaining the earlier viewer checks.

For an actual signed-in local Codex run:

```sh
uv run python -m examples.planning_case --project results/planning-codex
uv run project-memory setup --project results/planning-codex --client codex --trust --no-view
uv run python -m examples.codex_planning --project results/planning-codex --output results/planning-run
uv run python -m examples.context_audit results/planning-run
```

The input audit deliberately exits unsuccessfully when the target is not met. The harness defaults to a 600-second deadline and records a timed-out run explicitly. To exercise recovery, use `--timeout 240`, inspect the result and existing effects, and resume a timed-out task using its returned thread ID:

```sh
uv run python -m examples.codex_planning --project results/planning-codex --output results/planning-recovery --resume-thread THREAD_ID
```

A timeout does not guarantee interruption at a particular action. Never reseed the directory or repeat an unconfirmed command merely to obtain a clean result. Recovery does not run an independent shell test automatically; it must inspect the earlier evidence. Raw logs can contain user data and should remain private.

The first CI run passed Chromium and both Python versions on Linux and macOS, but failed on Windows during test cleanup. The new test used signal zero to poll a terminated process; on Windows that triggered a console interrupt and left the test database open. Cleanup now polls the owned HTTP endpoint, as the existing restart check does. A subsequent Windows run exposed an existing teardown race: deleting the database immediately after termination could precede process exit. The live-process tests now retain their real child-process handles and wait for exit before deleting temporary files. The failed run remains available as [CI evidence](https://github.com/Dankaro-projects/project-memory/actions/runs/34842932721).

## Remaining limits

This provides more reliable continuity within an active host session, not unattended project management. It does not infer product intent perfectly, authenticate stored authority, claim an operating-system execution lock or automatically accept lessons. The assistant must still record significant changes and assess their meaning. Large complete plans can exceed a requested response budget and fail explicitly; evidence is not silently dropped.

Daily reminder frequency, human corrections, repeated research, net maintenance time, long-term drift and competitor performance remain unmeasured. This iteration adds no runtime dependency, database table, background agent or new approval administration. Those architectural facts do not prove low total maintenance cost. The next meaningful evaluation is ordinary project work over multiple sessions, including failures and changed requirements.
